# Автоматизація процесу «первинний відбір → шортлист → передача клієнту»
### Технічна архітектура під поточну стадію metaprofile ATS

**Головна теза:** нову центральну систему будувати НЕ треба. Ваш власний ATS (metaprofile на
Supabase + React) уже реалізує ~85% описаного процесу. Реальне завдання — закрити **4 прогалини**
і додати **одну керуючу дію** (оркестрацію). Нижче — що вже є, чого бракує, і три варіанти
реалізації з цифрами.

---

## 1. Що вже побудовано (звірено з кодом)

| Крок процесу | Статус | Наявний компонент у metaprofile |
|---|---|---|
| Відбір за критеріями вакансії/стратегії | ✅ Є | `generate-search-strategy`, `recommend-candidates`, воронка, matching |
| Первинна зустріч, переміщення у шортлист | ✅ Є | Воронка (`list_state`/stages), `schedule-interview` |
| Структурована співбесіда за компетенціями | ✅ Є | `conduct-interview`, матриця `vacancy_competencies` |
| Оцінка компетенцій за шкалою | ✅ Є | `competency_scores`, `_ats_competency_scale`, пороги high/medium |
| Збір матеріалів (вакансія, бриф, стратегія, резюме, оцінки, коментарі) | ✅ Є | `parse-brief`, `parse-resume`, `import-vacancy`, поля картки |
| Транскрипт співбесіди | ⚠️ Частково | `fetch-meet-transcript` — тягне **готовий** транскрипт Google Meet; **сирий запис не транскрибує** |
| AI-звіт із розділенням факт/оцінка/висновок, «не вигадувати» | ✅ Є | `generate-candidate-report` (Claude sonnet-4-6): матриця+оцінки, доказовість, факт/оцінка/припущення |
| Звіт у markdown, ручне редагування | ✅ Є | `reports.content_md`, статуси, публічне посилання (`_ats_report_public_link`) |
| Корпоративний DOCX + версії + PDF | ❌ Немає | у коді прямо позначено «поза скоупом MVP» |
| Клієнтський портал — перегляд звітів/резюме | ✅ Є | `public-client-portal`, `public-report`, прапорці розділів |
| Клієнт: свої оцінки/статуси/коментар/причина/дата зустрічі | ⚠️ Частково | портал показує звіти; **інтерактивний зворотний зв'язок неповний** |
| Сповіщення рекрутеру | ✅ Є (база) | `notify`, `_ats_notifications` — треба під'єднати до подій порталу |
| GDPR: стирання, журнал, доступи | ✅ Є | `erase-candidate`, `log-application-event`, `grant-management` (RBAC) |
| Офери | ✅ Є | модуль оферів |
| «Одна керуюча дія» (весь ланцюг одним запуском) | ❌ Немає | кроки існують окремими Edge, не зшиті в один конвеєр |

**Отже, 4 реальні прогалини:**
1. **Транскрибація сирого запису** (аудіо/відео → текст), укр. мова — зараз лише Meet-транскрипт.
2. **Корпоративний DOCX → PDF + контроль версій** звіту.
3. **Інтерактив клієнта в порталі**: власні оцінки, статуси (запросити / продовжити / відкласти /
   інша позиція / відмовити), причина відмови, пропозиція дати + запис у історію + сповіщення рекрутеру.
4. **Оркестрація «одна кнопка»**: запис → транскрипт → збір → AI-аналіз → чернетка → погодження →
   стиль → PDF → публікація → фіксація фідбеку.

## 2. Відповіді на завдання (10 пунктів)

**1) Центральна система.** Ваш **власний ATS (metaprofile)** — і має лишитися нею. Дані кандидатів,
вакансій, оцінок, звітів, порталу вже там, з RLS і журналюванням. Airtable/CRM як «центр» були б
кроком назад (дублювання даних, слабший GDPR-контроль). Зовнішні інструменти під'єднуємо як
периферію до ATS, а не навпаки.

**2) AI-інструменти.**
- *Транскрибація:* OpenAI `gpt-4o-mini-transcribe` (~$0.18/год) або Whisper; альтернативи —
  Deepgram Nova-3 (~$0.26/год), AssemblyAI ($0.15–0.21/год). Усі підтримують українську
  (Whisper/Deepgram — найкраще для UA; AssemblyAI — 99 мов). ~1-год співбесіда ≈ $0.15–0.30.
- *Аналіз резюме/транскрипції, оцінка відповідності, звіт:* **вже використовуєте Claude
  (sonnet-4-6)** у `generate-candidate-report`. Це і є правильний вибір; ~$0.20–0.50 за звіт.
- Окремий «оцінювач відповідності» не потрібен — він уже в звіті (зважений бал по матриці + пороги).

**3) Оркестрація.** Два підходи: (а) **n8n** як зовнішній диригент (швидко, візуально) або
(б) нативний **edge-конвеєр** у Supabase (`run-candidate-pipeline`) зі статусами кроків. Рекомендація —
n8n **лише для важкого асинхрону** (запис→транскрибація), решту тримати в ATS.

**4) Редагований документ + PDF.** DOCX-шаблон у корпоративному стилі (лого, шрифти, кольори
індиго/оранж) → рендер зі змінними → **Gotenberg** (LibreOffice, self-host, безкоштовно) або
CloudConvert (~$0.02/конв.) у PDF. Версії — таблиця `report_versions` (кожне збереження = нова версія).
Редагування лишається в markdown/редакторі ATS до фіналізації.

**5) Клієнтська таблиця/кабінет.** У вас вже є `public-client-portal`. Дороблюємо: єдина таблиця
шортлиста + на кожного кандидата дії (свої оцінки, статус із 5 варіантів, коментар, причина відмови,
пропозиція дати). Пишемо у `client_feedback`/історію. Не потрібен зовнішній кабінет.

**6) Сповіщення рекрутеру.** `notify` + `_ats_notifications` вже є — вішаємо тригер на зміну статусу/
коментар у порталі (email + в застосунку). Опційно — миттєвий вебхук у Slack/Telegram.

**7) GDPR / доступи / захист / журнал.** Основа є: RLS (розмежування), `grant-management` (ролі),
`erase-candidate` (право на стирання), `log-application-event` (журнал дій). Додати: згода кандидата
(підстава обробки), строк зберігання/автовидалення, доступ клієнта лише через токен-посилання з
терміном дії, шифрування записів у Storage, DPA з вендорами транскрибації (зберігати аудіо в ЄС/
видаляти після транскрипту).

**8) Готові продукти, що закривають частини.** Транскрибація — AssemblyAI/Deepgram/OpenAI/**Fireflies**
(вже маєте конектор fetch-meet). Оркестрація — n8n/Make. DOCX→PDF — Gotenberg/CloudConvert/**Carbone**.
Аналіз/звіт — Claude (є). Повністю «під ключ» ваш процес жоден готовий продукт не закриває — бо
логіка компетенцій+бренд+портал уже кастомні.

**9) Що розробляти окремо.** (а) `transcribe-recording` edge; (б) `render-report-docx` + PDF + версії;
(в) інтерактив порталу (оцінки/статуси/історія) + тригер сповіщень; (г) `run-candidate-pipeline`
(одна кнопка) зі станами й ручним re-run окремих кроків.

**10) Вартість/терміни — див. розділ 3 по кожному варіанту.**

## 3. Три варіанти реалізації

> Примітка щодо вартості: розробка у вас ведеться через цього асистента (без окремого підрядника),
> тож головний «кошт» — час, а не гонорари. Нижче — інфраструктурні витрати + орієнтовний обсяг робіт.

### Варіант A — Швидкий MVP (no-code/low-code)
**Інструменти:** наявний ATS (система-запису) + **n8n** (диригент) + транскрибація-API + **Google Docs
шаблон / Carbone** для стилю + Gotenberg/CloudConvert для PDF. Фідбек клієнта — тимчасово через
**Tally/Airtable** (якщо не чіпати портал).
**Схема даних:** ATS (вебхук «запис готовий») → n8n → транскрибація-API → виклик `generate-candidate-report`
(вже є) → рендер DOCX→PDF → запис файлу назад в ATS (Storage) → публічне посилання → фідбек у
Airtable → n8n повертає у `notify`.
**Послідовність:** 1 вебхук з ATS запускає сценарій n8n на всі кроки.
**Переваги:** запуск за 1–2 тижні; візуально, легко міняти; мінімум коду.
**Обмеження/ризики:** дані частково «гуляють» через n8n і Airtable (GDPR-ризик), крихкість інтеграцій,
дубль джерела істини для фідбеку, менший контроль версій.
**Запуск:** ~1–2 тижні. **Регулярно:** n8n cloud $24/міс (або self-host $15) + транскрибація/LLM за
обсягом (~$50–150) → **~$80–200/міс**.

### Варіант B — Збалансоване рішення (РЕКОМЕНДОВАНО)
**Інструменти:** розширюємо **сам ATS** нативно + **n8n лише для асинхрону** транскрибації.
Нове: `transcribe-recording` (Deepgram/OpenAI, UA), `render-report-docx`+Gotenberg PDF+`report_versions`,
інтерактив порталу (`client_feedback`+статуси+історія), `run-candidate-pipeline` (одна кнопка зі станами).
**Схема даних:** усе в Supabase (Postgres+Storage+RLS). Запис → `transcribe-recording` (n8n тримає
довгий job і б'є вебхуком назад) → `generate-candidate-report` → `render-report-docx`→PDF (Storage,
версії) → публікація в наявний портал → клієнт ставить статус/оцінки → тригер `notify` рекрутеру →
все в історії кандидата.
**Послідовність:** одна кнопка «Сформувати звіт» на картці → конвеєр із кроками, кожен з яких можна
перезапустити вручну; рекрутер погоджує чернетку перед стилізацією/PDF/публікацією.
**Переваги:** максимально використовує вже вкладене; єдине джерело істини; найкращий GDPR-контроль;
бренд і компетенції — нативні; мінімум нових вендорів.
**Обмеження/ризики:** потрібна розробка 3–4 edge + доробка порталу; n8n лишається однією зовнішньою
залежністю (можна прибрати у Варіанті C).
**Запуск:** ~3–5 тижнів роботи. **Регулярно:** Supabase Pro $25 + n8n self-host $15 + транскрибація/LLM
$50–150 + Gotenberg (self-host, $0) → **~$90–200/міс**.

### Варіант C — Повноцінна власна система
**Інструменти:** усе нативно, без зовнішнього диригента. Оркестрація — черги в Postgres
(pg-boss / Supabase Queues) + edge; транскрибація — або API, або **self-host Whisper** (faster-whisper
на GPU-VPS) для повного контролю даних; власний рендер DOCX/PDF; власний клієнтський кабінет (розширення
наявного порталу до повноцінного).
**Схема даних:** повністю всередині вашого периметра; аудіо не виходить до зовнішніх API (якщо self-host
Whisper) — найсильніший GDPR-аргумент для чутливих клієнтів.
**Послідовність:** та сама «одна кнопка», але оркестрація й транскрибація — свої, черги зі станами,
ретраями, ідемпотентністю.
**Переваги:** максимальний контроль, незалежність від вендорів, найкращий для enterprise/держ-клієнтів,
дані не покидають ЄС/ваш сервер.
**Обмеження/ризики:** найбільший обсяг розробки й підтримки; GPU-хостинг для Whisper коштує дорожче;
ви берете на себе надійність черг/ретраїв.
**Запуск:** ~8–12 тижнів. **Регулярно:** Supabase Pro $25 + GPU-VPS для Whisper $80–250 (або API $50–150)
+ інфра → **~$150–400/міс**.

## 4. Рекомендація

Ідіть **Варіантом B**. Ви вже маєте кастомний ATS, що покриває більшість процесу, тож «повний кастом»
(C) — це переважно дублювання вже зробленого заради self-host транскрибації, а «MVP» (A) розмиває
дані по n8n/Airtable і б'є по GDPR. B закриває саме 4 прогалини нативно, лишає одну зовнішню залежність
(n8n лише для довгих job транскрибації) і зберігає єдине джерело істини.

**Порядок робіт у Варіанті B (можу вести інкрементально, не ламаючи наявне):**
1. `transcribe-recording` (запис зі Storage/Drive → Deepgram/OpenAI → `interviews.transcript`).
2. `render-report-docx` + Gotenberg PDF + `report_versions` (корпоративний шаблон індиго/оранж).
3. Інтерактив порталу: оцінки/статуси/причина/дата → `client_feedback` + історія + тригер `notify`.
4. `run-candidate-pipeline` — «одна кнопка» зі станами кроків і ручним re-run.
5. GDPR-докрутки: згода/строк зберігання/автовидалення аудіо + DPA з вендором транскрибації.

**Орієнтир для B:** ~3–5 тижнів інкрементальної розробки, регулярні витрати ~$90–200/міс.
