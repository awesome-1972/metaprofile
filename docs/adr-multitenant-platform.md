# ADR — Мультитенантна платформа: тенанти, рівні, файли Drive, ролі, трекер задач

**Дата:** 2026-07-27
**Статус:** чернетка на затвердження власником
**Автор:** архітектурний прохід перед реалізацією
**Вхід:** структура реальних проектів у Google Drive (2 клієнти, вакансії CFO/CCO/CED,
Red Cross HRD), поточна схема БД, попередні рішення власника.

> Це план ПЕРЕД кодом. Реалізація — окремими фазами після затвердження.
> Мультитенант — фундамент: усе інше будується вже в його парадигмі, щоб не
> переробляти RLS двічі.

---

## 0. Цільова ієрархія (підтверджена з Drive)

```
MetaVision Consulting        ← тенант (компанія-власник платформи)
  └─ Клієнт / Проект         ← напр. «Червоний Хрест»; кілька вакансій
       └─ Вакансія            ← CFO, CCO, Chief Expansion Director…
            ├─ Воронка (етапи → стадії)   ✅ вже є
            ├─ Артефакти (структуровані)  ✅ здебільшого є
            └─ Файли (CV, відео, транскрипти, презентації, договори)  ⛔ нема
```

**Набір артефактів на вакансію** (з Drive, майже все вже ведеться в БД):

| Артефакт у Drive | Стан у платформі |
|---|---|
| Стратегія пошуку | ✅ `vacancy_search_strategies` |
| Матриця компетенцій | ✅ `vacancy_competencies` |
| Бріф для кандидатів / Комунікація посади | ✅ `vacancy_public_briefs` |
| Long List | ✅ імпорт Excel → `applications` |
| Промт оцінки співбесіди | ✅ `vacancy_prompts` |
| Reports (AI-звіти) | ✅ `candidate_reports` |
| Video interviews / Voice-to-Text | ✅ `interviews` (+транскрипт) |
| **CVs (файли резюме)** | ⛔ парситься, але файл не зберігається |
| **Presentation to Client** | ⛔ нема |
| **Contracts / Договір, From Client** | ⛔ нема |
| **Recruitment Task Tracker** | 🟡 частково (SLA-світлофор ≠ план задач) |

Висновок: ядро артефактів уже структуроване. Бракує **файлового шару** і **трекера
задач проекту**. Плюс — обгортка **мультитенанта** над усім.

## 1. Рівні: 2 (клієнт=проект) vs 3 (клієнт→проект→вакансія)

Поточна БД: `vacancies.hiring_project_id` (NOT NULL) → `hiring_projects.client_id`
(NOT NULL) → `clients`. Вакансія прямого `client_id` **не має**.

### Варіант A — 2 рівні (клієнт = проект → вакансія)

**За:**
- Збігається з Drive: там клієнт містить вакансії напряму, проміжного рівня немає.
- Простіша ментальна модель для рекрутера («клієнт → його вакансії»).
- Менше кліків, менше сутностей в UI.

**Проти:**
- Міграція даних: перенести `vacancies.hiring_project_id` → `client_id`, злити
  `hiring_projects` у `clients` (перенести name/status/dates), переписати RLS
  (`mp_can_access_project` зникає, scope спрощується). Незворотно.
- Втрачаємо групування «кілька хвиль пошуку на одного клієнта в часі» (напр.
  клієнт повертається за рік — нова хвиля з тими самими вакансіями).
- `hiring_projects` уже вплетений у ~8 RLS-функцій і requisition-flow.

### Варіант B — залишити 3 рівні, перейменувати в UI

**За:**
- Нуль міграції даних і RLS — лише перейменування у UI: `hiring_project` →
  показувати як «Проект», `client` → «Клієнт/Компанія».
- Гнучкість: клієнт → кілька проектів (хвиль) → вакансії. Requisition-flow на
  проект уже працює.
- Найменший ризик.

**Проти:**
- Зайвий рівень, якого немає в Drive — рекрутер щоразу створює «проект»
  всередині клієнта. Можна пом'якшити: авто-створювати дефолтний проект при
  створенні клієнта (1 клік замість 2).

### Рекомендація архітектора: **Варіант B + авто-дефолтний проект**

Причина: 3-рівнева схема вже глибоко вплетена в RLS і requisition. Переробляти її
під час мультитенант-міграції = два ризикових рефакторинги RLS одночасно. Дешевше
й безпечніше: лишити 3 рівні, у UI назвати клієнт=«Клієнт», hiring_project=«Проект»,
і при створенні клієнта авто-створювати один проект «Основний» — тоді для простих
випадків рекрутер бачить фактично 2 рівні, а гнучкість 3-го лишається для складних.

Остаточне рішення — за власником (див. §7, питання 1).

## 2. Мультитенант — фундамент

### 2.1 Модель

Нова коренева таблиця `tenants` (MetaVision — перший і поки єдиний). `tenant_id`
додається на **кореневі** сутності: `clients`, `profiles`/`user_roles`,
довідники (`candidate_sources`, `rejection_reasons`, `message_templates`,
`pipeline_stage_templates`). Дочірні (`hiring_projects`, `vacancies`,
`applications`, `pipeline_stages`, `search_phases`, усі артефакти) **успадковують**
тенант через ланцюг FK — денормалізувати `tenant_id` на них НЕ обов'язково, якщо
RLS резолвить тенант через parent. Але для швидкості RLS — денормалізація
`tenant_id` на «гарячих» таблицях (`vacancies`, `applications`) виправдана.

### 2.2 RLS-стратегія (головний ризик)

- Нова helper-функція `mp_current_tenant()` — тенант поточного користувача
  (з `user_roles`/`profiles`). Кешується як STABLE.
- **Кожна** політика отримує tenant-предикат: `tenant_id = mp_current_tenant()`.
  Це має бути в КОЖНІЙ таблиці — пропуск = горизонтальний витік між тенантами.
- Наявні `mp_can_*` helper'и доповнюються tenant-перевіркою (не замінюються —
  scope всередині тенанта лишається).
- **Обов'язково**: агент `security` робить повний аудит RLS після міграції —
  жодної таблиці без tenant-предиката.

### 2.3 Кандидати — крос-тенантні чи ізольовані?

Розвилка (§7, питання 2): `ats_candidates` — спільна база на весь MetaVision, чи
ізольована на тенант? Для агенції один MetaVision-тенант → байдуже зараз, але
якщо продавати платформу іншим агенціям — кандидати МАЮТЬ бути ізольовані на
тенант (GDPR + конкуренція). Рекомендація: `ats_candidates.tenant_id` з першого дня.

### 2.4 Дашборд на тенант

Головна сторінка тенанта: активні проекти/вакансії, воронка-зведення, SLA-світлофор
по всіх вакансіях, найближчі дедлайни трекера, «завислі» кандидати. Будується
на наявних даних + новий трекер (§4).

## 3. Файли Drive — авто-папки + лінки в БД

Рішення власника: **файли на Drive, метадані/лінки в Postgres** (авто-створення
структури папок).

### 3.1 Модель

Нова таблиця `vacancy_files` (або ширше `entity_files` з поліморфним власником):
```
id, tenant_id, vacancy_id, candidate_id (nullable), category, drive_file_id,
drive_folder_id, name, mime_type, web_view_link, uploaded_by, created_at
```
`category` (enum): `long_list | cv | interview_video | transcript | competency_matrix
| public_brief | report | client_presentation | contract | from_client | other`.

### 3.2 Авто-структура папок

При створенні вакансії Edge-функція (service account, Domain-wide Delegation — вже
налаштовано для Calendar/Meet) створює в Drive під клієнтом папку вакансії з
підпапками за категоріями (Long List, CVs, Матриця, Reports, Presentation to
Client…) — дзеркало реальної структури. `drive_folder_id` пишеться у `vacancies`.

### 3.3 CV → парсинг по полях

CV завантажується (UI або кладеться в Drive-папку) → `parse-resume` (вже є) →
поля кандидата (ПІБ, контакти, досвід, компанія) авто-заповнюються, файл лінкується
через `vacancy_files.category='cv'`. Це і є «розкладка по полях», яку просив власник.

### 3.4 Обмеження

Google Drive API через сервісний акаунт: квоти, права на папки клієнта. Створення
папок — так; двостороння синхронізація (зміни в Drive ↔ БД) — НЕ робимо (складно,
конфлікти). Drive — сховище файлів, БД — джерело правди про сутності.

## 4. Трекер задач проекту (Recruitment Task Tracker)

Реальний трекер — план проекту з 14 задач по пунктах договору. Це окрема сутність,
ширша за SLA-світлофор.

### 4.1 Модель

`project_tasks`:
```
id, tenant_id, hiring_project_id (або vacancy_id), position, direction (напрям),
title, contract_ref (пункт договору), start_date, due_date, duration_days,
status (planned|in_progress|done|paused|cancelled), assignee, depends_on (uuid[]),
artifact_result, artifact_link, notes
```

### 4.2 Шаблон 14 задач за замовчуванням

При старті проекту засівається шаблон із 14 задач (Запуск → Матриця → Стратегія →
Бенчмарк → Довгий список → Скринінг → Короткий список → Матриця оцінки → Розгляд
замовником → Рекомендації → Офер → Сесія очікувань → Психометрика → Щотижнева
звітність) з типовими тривалостями й залежностями. Редагується під проект.

### 4.3 Зв'язок зі SLA-світлофором

Трекер задач (план проекту) і SLA-світлофор (старіння кандидатів на стадіях) —
доповнюють одне одного: перший про ПРОЕКТ, другий про КАНДИДАТІВ. Обидва живлять
дашборд тенанта. Задачі можуть посилатися на артефакти (§3) через `artifact_link`.

## 5. Рольова модель

Рішення власника: **Адмін=admin, Партнер=owner, Рекрутер=recruiter, Відвідувач=нова**.

| Роль | Наявна | Права |
|---|---|---|
| **Адмін** | `admin` | окремий інтерфейс налаштувань тенанта: користувачі, ролі, шаблони, інтеграції, білінг. Повний доступ. |
| **Партнер** | `owner` | усі проекти/вакансії тенанта, фінанси, затвердження requisition, звіти клієнту. |
| **Рекрутер** | `recruiter` | свої вакансії (assigned), кандидати, воронка, комунікації. Без фінансів поза scope. |
| **Відвідувач** | **нова `visitor`** | read-only: бачить призначене, не змінює. Для клієнта/спостерігача/стажера. |

- `assistant` → мапиться у «Відвідувач» або лишається технічною (рішення §7, п.3).
- Нова роль `visitor` — enum `app_role += 'visitor'` (окрема міграція, як завжди).
- **Адмін-інтерфейс** — окремий розділ `/admin/*` (ProtectedRoute allowedRoles=['admin']):
  налаштування тенанта, керування користувачами (вже є `/ats/users`), шаблони
  воронки/листів, інтеграції (Drive/Google/Resend), майбутній білінг.

## 6. Послідовність упровадження (фази)

Порядок продиктований залежностями: тенант — фундамент, решта — зверху.

| Фаза | Зміст | Effort | Залежить від |
|---|---|---|---|
| **0. ADR** (цей документ) | затвердження рішень власником | — | — |
| **1. Мультитенант-фундамент** | `tenants`, `tenant_id`, `mp_current_tenant`, переписати RLS, аудит security-агентом, backfill (усе → тенант MetaVision) | **XL** | 0 |
| **2. Рольова модель** | `visitor`, адмін-інтерфейс `/admin`, розмежування прав | **M** | 1 |
| **3. Файли Drive** | `vacancy_files`, авто-папки (Edge), CV→парсинг→лінк, UI завантаження/перегляду | **L** | 1 |
| **4. Трекер задач** | `project_tasks`, шаблон 14 задач, UI план-таблиця, дашборд тенанта | **L** | 1 |
| **5. Рівні (за рішенням)** | якщо Варіант A — злиття hiring_projects; якщо B — лише UI-перейменування | **S** (B) / **L** (A) | 1 |
| **6. GDPR-згода** | consent при першому запрошенні (metavision.ua/gdpr), retention | **M** | 1 |

Кожна фаза — окремий цикл: міграція → хуки → UI → верифікація (typecheck/lint на
git-еталоні) → міграція в прод через SQL Editor (CLI push не працює).

## 7. Рішення власника (затверджено 2026-07-27)

1. **Рівні:** ✅ **Варіант B** — 3 рівні + авто-дефолтний проект при створенні клієнта.
2. **Кандидати:** ✅ **спільна база в межах тенанта** з централізованим пошуком
   (крос-вакансійна), АЛЕ `ats_candidates.tenant_id` є — ізоляція МІЖ тенантами
   (агенціями). Всередині MetaVision база спільна; інша агенція своїх не бачить.
3. **Ролі:** ✅ базові ролі (owner/recruiter/assistant/admin) лишаються технічними,
   ПЛЮС **кастомні ролі під запит**. Отже рольова модель = гібрид: системні ролі +
   таблиця `roles`(tenant_id, name, permissions) + `role_permissions`. Це апгрейд
   фази 2 (RBAC замість простого enum).
4. **Файли CV:** ✅ **обидва шляхи** — і завантаження через UI, і підхоплення з
   Drive-папки, з **перевіркою дублів** (за хешем/іменем/Drive-file-id).
5. **Продуктизація:** ✅ ізолювати тенанти **вже зараз**. Горизонт продажу — **~0.5
   року (≈ січень 2027)**. Отже мультитенант має бути production-grade, не заглушка.

### Наслідки для плану
- Фаза 2 (ролі) розширюється: **RBAC із кастомними ролями** (не просто `+visitor`).
- Кандидати: `tenant_id` так, але без під-ізоляції всередині тенанта (спільний пул).
- Продаж за 0.5 року → RLS-ізоляція тенантів має бути завершена й проаудитована
  задовго до того; фаза 1 стає критичною за якістю.

### Інкрементальна стратегія фази 1 (щоб не зламати живе)
Оскільки тенант поки один (MetaVision), робимо у два під-кроки:
- **1a — структура без ізоляції:** `tenants`, `tenant_id` на всіх кореневих +
  гарячих таблицях, backfill усе → MetaVision, `mp_current_tenant()`. RLS НЕ чіпаємо
  — усі в одному тенанті, поведінка не змінюється (нульовий ризик регресу).
- **1b — ізоляція:** tenant-предикат у кожну RLS-політику + повний аудит
  security-агентом. Вмикається перед появою 2-го тенанта / продажем.

## Підсумок

Ядро ATS уже сильне й структуроване — Drive це підтвердив (майже всі артефакти вже
в БД). Бракує трьох речей: **мультитенант-обгортки** (фундамент), **файлового шару
на Drive** і **трекера задач проекту**. Будуємо в цьому порядку, бо тенант — під
усе інше. Рівні (2 vs 3) і кандидати (ізоляція) — два рішення, що визначають обсяг;
рекомендація — мінімальний ризик (3 рівні + авто-проект, кандидати ізольовані).
Кожна фаза проходить аудит безпеки RLS перед продом — це найдорожча помилка, якщо
пропустити tenant-предикат.
