## ✅ Зроблено (в проді)

### Ядро ATS (раніше)
Клієнти → проекти найму → вакансії (Бріф/Компетенції/Звіти/Порівняння/Списки) →
kanban-воронка з DnD → кандидати → комунікації (Resend, масові) → резюме-парсинг (AI) →
скоринг компетенцій → AI-звіти (per-vacancy промти) → Google Calendar/Meet +
транскрипти. Онбординг користувачів, ролі, гранти доступу, requisition-flow.

### Процес пошуку — 6 етапів (сесії 13.07)
- Двоповерхова воронка: **етапи пошуку → своя воронка стадій** у кожному.
- Етап 1 «Підготовка» без кандидатів: чеклист, стратегія пошуку, бріф для кандидатів
  (AI-чернетка → PDF), матриця компетенцій, план проекту.
- Наскрізний вигляд воронки з поділом кольором + **гнучке налаштування** (додавання
  етапів/стадій під запит, FunnelEditor).
- **Тайм-трекер SLA** — світлофор (кандидат на стадії + етап vs план), блок «Завислі».
- **Шаблони листів** (відмова/запрошення по етапах) + AI-чернетка + дії на картці.
- **Імпорт лонг-листа з Excel** з дедупом + табличний вигляд етапу.

### Фаза 1 — Мультитенант (27.07)
- Таблиця `tenants`, `tenant_id` на всіх таблицях, `mp_current_tenant()` (з fallback
  на MetaVision), stamp-тригери, RESTRICTIVE tenant-gate (ізоляція між тенантами).
- Тенантизовано `mp_can_*` helper'и + Edge-функції (інвайти, grant, erase, seed).
- Identity-таблиці (profiles/user_roles/roles) — без жорсткого gate (fallback tenant),
  щоб не ламати вхід; повна ізоляція для 2-го тенанта — окремо.
- Кандидати — спільна база в межах тенанта, ізольована між тенантами.

### Фаза 2 — Ролі (RBAC) + архів + стоп-лист (27.07)
- **RBAC**: таблиця `roles` (системні + кастомні), `permissions text[]` (21 право
  `домен.дія`), helper'и `mp_has_permission`/`mp_my_permissions`, хук `usePermissions().can()`.
- **5 системних ролей** із пресетами: Адмін / Партнер / Рекрутер / Асистент / Відвідувач.
- **Адмін-UI `/ats/roles`**: редактор прав галочками, створення/видалення кастомних ролей.
- **Призначення кастомних ролей користувачам** — секція в картці користувача.
- **Гейтинг дій за правами** (`can()`): архів/редагування клієнтів і проектів.
- **Архівування/редагування** клієнтів і проектів (+ фільтр «Архів» у списках).
- **Стоп-лист вакансії** (заборонені клієнтом кандидати) + автоперевірка нового кандидата.

### Агенти проєкту
`.claude/agents/`: backend, frontend, architect, qa, security, analytics, web-designer.

### Фаза 3 — Файли на Google Drive (в роботі, поетапно 1→2→3)
- **Крок 1 (зроблено, чекає push):** таблиця `vacancy_files` (метадані + Drive-лінки за
  категоріями-папками), хук `use-vacancy-files`, вкладка **«Файли»** на вакансії з
  8 папками (Long List, CVs, Матриця, Reports, Presentation, Contracts, From Client,
  Voice-to-Text) + дедуп за `drive_file_id`/іменем. Структура папок — як у реальних
  проєктах агенції. Гейт `files.manage`. Одна коренева папка MetaVision (рішення власника).
- **Крок 2 (далі):** CV → парсер → авто-розкладка по полях кандидата (парсер уже є).
- **Крок 3 (далі):** авто-створення структури папок Drive сервісним акаунтом при
  створенні вакансії; підхоплення файлів із Drive-папки; обидва шляхи завантаження.
Drive — сховище, Postgres — джерело правди. Сервісний акаунт уже налаштований (Calendar/Meet);
для запису в Drive знадобиться scope `drive` (зараз лише `drive.readonly`).

## ⏳ За планом

### Фаза 4 — Трекер задач проекту
Окрема сутність `project_tasks` за зразком Recruitment Task Tracker: 14 задач по пунктах
договору (напрям, дедлайн, залежності, артефакт, статус). Шаблон за замовчуванням +
дашборд тенанта.

### Фаза 5 — Рівні (за рішенням: Варіант B)
3 рівні (клієнт → проект → вакансія) + авто-створення дефолтного проекту при створенні
клієнта (щоб для простих випадків виглядало як 2 рівні). Мінімальна робота.

### Фаза 6 — GDPR-згода
Consent на обробку ПД при першому запрошенні (лінк metavision.ua/gdpr), retention/дата
видалення. EU AI Act — ворота перед продуктизацією.

### Хвіст безпеки (перед 2-м тенантом / продажем ~01.2027)
- Повернути ізоляцію identity-таблиць коректно (NULL-толерантний gate або фільтр у коді).
- Прибрати fallback у `mp_current_tenant` (fail-closed для відсутнього профілю).
- Аудит Edge під service_role на tenant-фільтри (більшість закрита, дозакрити хвіст).

### Дрібне шліфування
- Застосувати `can()` ширше (фінанси, керування, створення вакансій) замість `isInternal`.
- Прибрати/сховати стару V1-демо та V2 job-board (щоб не плутали з ATS) — рішення власника.

## Урок процесу (важливо)
Міграції накочувати **тільки через `supabase db push` з паролем БД**
(`$env:SUPABASE_DB_PASSWORD`), НЕ вручну — інакше журнал розсинхронюється з реальністю.
Після міграції звіряти реальні обʼєкти (`to_regclass`), не лише журнал. Деталі пасток —
пам'ять `metaprofile-multitenant-traps`.
